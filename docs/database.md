# FlowOps Database Design (Phase 2)

PostgreSQL relational schema derived from `docs/domain-model.md` and CLAUDE.md §7. This is a design
document — no migration, `DbContext`, or entity configuration is created by it. Naming convention:
snake_case via `EFCore.NamingConventions`, per CLAUDE.md §7.1.

Every table lists its **grain** (what one row represents). No table or relationship is proposed that
does not trace to a rule in `docs/domain-model.md`. Where a value is computed rather than stored,
it is called out explicitly under "Derived, not stored" at the end of this document — it does not
get a column.

---

## 1. Identity tables (owned by Infrastructure, not designed here)

`AspNetUsers`, `AspNetRoles`, `AspNetUserRoles`, etc. are generated by ASP.NET Core Identity
(`IdentityDbContext<ApplicationUser, ApplicationRole, Guid>`) and are not redesigned in this
document. FlowOps extends `AspNetUsers` with additional columns on `ApplicationUser`
(`TICKET-ENT-04`, `AUTH-RULE-01`):

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `display_name` | `text` | No | Shown in place of email anywhere a user is referenced (CLAUDE.md §12: never log/display raw PII beyond what Identity already needs) |
| `job_title` | `text` | Yes | Descriptive only, no business rule depends on it |
| `is_active` | `boolean` | No, default `true` | An inactive user cannot be an active team member (`TICKET-INV-03`) or hold assignment; also the mechanism both self-account deletion (Phase 17) and platform user deactivation (Phase 24, ADR-0023) use to stop authentication |
| `primary_team_id` | `int` (FK → `teams.id`, `ON DELETE SET NULL`) | Yes | Primary team is informational; team *membership* (which drives authorization) is `team_members`, not this column |
| `appearance` | `varchar(10)` | No, default `'Dark'` | Phase 29C: the user's own Dark / Light / System choice, stored as text (ADR-0009) with check `ck_users_appearance`. `System` is stored as itself, never as a resolved value. Existing users received `Dark` from the column default. |
| `is_demo_protected` | `boolean` | No, default `false` | CLAUDE.md §14's demo-mode guard — true only for accounts a demo seeding run created |
| `is_platform_admin` | `boolean` | No, default `false` | Phase 24 (ADR-0023): platform-wide authority, completely independent of `organization_memberships.role`. Set only by the `grant-platform-admin`/`revoke-platform-admin` startup CLI commands — never by any HTTP-reachable path |
| `registration_approved_at` | `timestamptz` | Yes | Phase 24A (ADR-0024): `NULL` until a Platform Admin approves the account. Together with `is_active`/`registration_rejected_at` this derives the account's four-state status — both null = Pending (cannot authenticate), `registration_rejected_at` set = Rejected (cannot authenticate, terminal), `registration_approved_at` set + `is_active` = Active, `registration_approved_at` set + not `is_active` = Inactive. Set once by `PlatformUserService.ApproveUserAsync`, or immediately at creation for an account created through invitation acceptance. The `approve-account` startup CLI command sets it directly, the same trust tier as `grant-platform-admin` — the only way to approve the very first Platform Admin's own (otherwise Pending) account |
| `registration_rejected_at` | `timestamptz` | Yes | Phase 24A-Extension (ADR-0025): `NULL` unless a Platform Admin rejected the account during initial review. Mutually exclusive with `registration_approved_at` by construction — only a Pending account (both still null) may ever be rejected (`AccountLifecyclePolicy.CanReject`). Set once by `PlatformUserService.RejectUserAsync`; terminal — never cleared by any existing operation |

No other Identity table is modified. The Domain never references `ApplicationUser` — see
`TICKET-ENT-04` and `docs/architecture.md` §2.

## 1a. `organizations` (`ORG-RULE-01`, CLAUDE.md §6.3)

**Grain:** one row = one tenant organization — the outer authorization boundary.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `int identity` | No | PK |
| `name` | `text` | No | |
| `created_at` | `timestamptz` | No | |
| `is_active` | `boolean` | No, default `true` | Phase 24 (ADR-0023): platform-level lifecycle, reversible (unlike Team/Category/Project deactivation, ADR-0022) — never cascades to any membership, team, category, project, ticket, comment, or event. `CurrentUserAccessor` simply stops resolving any membership into an inactive organization; Platform Admin's own queries are the one place still allowed to see it |

**Constraints:** none on `name` — deliberately not unique (Phase 17): two unrelated organizations
may register with the same display name (e.g. two independent "Acme Support" sign-ups). A prior
Phase 16 draft of this table had a global `UNIQUE (name)`, corrected once Phase 17's registration
flow made that constraint's real consequence — rejecting a legitimate second organization only
because another, unrelated one happened to pick the same name — concrete.
**Relationships:** `1:many` → `teams`, `projects`, `organization_memberships`.

## 1b. `organization_memberships` (`ORG-RULE-02`, CLAUDE.md §6.3)

**Grain:** one row = one user's membership in one organization, carrying that user's role
*within that organization* — the authoritative source of role, superseding ASP.NET Core Identity's
own per-user role assignment (kept only as an inert mirror; nothing reads it for authorization).

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `int identity` | No | PK — a surrogate key, unlike `team_members`' composite key, since no other table references a membership row by id today |
| `organization_id` | `int` (FK → `organizations.id`, `CASCADE`) | No | |
| `user_id` | `uuid` (FK → `AspNetUsers.Id`, `CASCADE`) | No | |
| `role` | `text` (CHECK: `UserRole` values) | No | |
| `joined_at` | `timestamptz` | No | |

**Constraints:** `UNIQUE (organization_id, user_id)` — a user belongs to a given organization at
most once.
**Relationships:** `many:many` between `organizations` and `AspNetUsers`, realized as this join
table. Unlike `team_members`, `CASCADE` delete is used (not `RESTRICT`): deleting an Organization
deletes its memberships along with it, since a membership has no meaning independent of the
organization it grants access to.

## 1c. `invitations` (`ORG-RULE-07`–`10`, CLAUDE.md §6.4, ADR-0017)

**Grain:** one row = one outstanding offer to join one organization with one role — not a
membership; accepting one creates a separate `organization_memberships` row.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `int identity` | No | PK |
| `organization_id` | `int` (FK → `organizations.id`, `RESTRICT`) | No | |
| `invited_email` | `text` | No | Original casing, shown back to the recipient on the accept page |
| `normalized_invited_email` | `text` | No | Identity's own `ILookupNormalizer` output — acceptance compares against this, never a hand-rolled comparison |
| `token_hash` | `varchar(64)` | No | SHA-256 of the raw bearer token, hex-encoded — the raw token itself is never persisted (ADR-0017) |
| `role` | `text` (CHECK: `UserRole` values) | No | The role the accepted membership will carry — never client-selectable at acceptance time |
| `invited_by_user_id` | `uuid` (FK → `AspNetUsers.Id`, `RESTRICT`) | No | |
| `created_at` | `timestamptz` | No | |
| `expires_at` | `timestamptz` | No | `created_at` + a fixed 7-day lifetime (`Invitation.DefaultLifetime`) |
| `accepted_at` | `timestamptz` | Yes | `NULL` until accepted; single-use is enforced by application logic plus the `xmin` concurrency token below, not by this column alone |

**Concurrency:** `xmin` optimistic-concurrency token (same mechanism as `tickets`, ADR-0011) —
required so two simultaneous acceptance attempts for the same token can never both succeed
(ADR-0017).
**Constraints:** `UNIQUE (token_hash)` — a lookup index as much as a constraint; a real hash
collision between two distinct tokens is cryptographically implausible. Deliberately **no** unique
constraint on email: the same address may legitimately hold outstanding invitations to several
different organizations at once.
**Indexes:** `(organization_id, normalized_invited_email)` — the "does a pending invitation already
exist for this email in this organization" lookup (Step 10's duplicate-invitation check).
**Relationships:** `many:1` → `organizations`; `many:1` → `AspNetUsers` (inviter only — there is no
FK to an invitee, since the invited email may not have an account yet).

## 2. `teams`

**Grain:** one row = one team (`TICKET-ENT-03`).

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `int identity` | No | PK |
| `organization_id` | `int` (FK → `organizations.id`, `RESTRICT`) | No | Phase 16, `ORG-RULE-01`: the outer tenancy boundary — added, not present before Phase 16 |
| `name` | `text` | No | |
| `created_at` | `timestamptz` | No | |
| `is_active` | `boolean` | No, default `true` | Phase 22 (ADR-0022): deactivation only, never a hard delete — never cascades to `categories`, `team_members`, or `tickets` |

**Constraints:** `UNIQUE (organization_id, name) WHERE is_active` — Phase 16 changed this from a
single global `UNIQUE (name)`, since two unrelated organizations must each be free to name a team
"Service Desk"; Phase 22 filtered it to active rows so a deactivated team's name is reusable.
**Relationships:** `1:many` → `team_members`, `categories`, `tickets` (via `team_id`); `many:1` →
`organizations`.

## 5a. `sprints` (`SPRINT-INV-01`–`06`, Phase 26, ADR-0029)

**Grain:** one row = one planning period of one project. Ticket membership is *not* a table: it is
`tickets.sprint_id` (a ticket is in at most one sprint by construction), and every membership change
is a `SprintChanged` `ticket_events` row.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `int identity` | No | PK |
| `project_id` | `int` (FK → `projects.id`, `RESTRICT`) | No | A sprint belongs to exactly one project; the organization is reached through it |
| `name` | `varchar(80)` | No | `SPRINT-INV-01` |
| `start_date` | `date` | No | UTC calendar date, inclusive (`SPRINT-INV-02`) |
| `end_date` | `date` | No | `CHECK (start_date <= end_date)` |
| `status` | `text` (CHECK: `Planned`, `Active`, `Completed`, `Cancelled`) | No | `SPRINT-INV-03`/`07`; persisted as text (ADR-0009) |
| `created_at` | `timestamptz` | No | |
| `activated_at` | `timestamptz` | Yes | Set when started |
| `completed_at` | `timestamptz` | Yes | `CHECK (status <> 'Completed' OR completed_at IS NOT NULL)` |
| *(concurrency token)* | PostgreSQL `xmin` | — | Two users starting/completing the same sprint: the loser gets a concurrency conflict (ADR-0011) |

**Constraints/indexes:** `UNIQUE (project_id) WHERE status = 'Active'` (`ux_sprints_one_active_per_project`
— at most one current sprint per project, on every code path); `(project_id, start_date)` for the
project's sprint list. Date-overlap between planned/active sprints is checked in `SprintService`, not
by an exclusion constraint (`SPRINT-INV-05`).
**Relationships:** `many:1` → `projects`; `1:many` → `tickets` (via `tickets.sprint_id`, `RESTRICT`,
sprints are never hard-deleted).

## 3. `team_members`

**Grain:** one row = one user's membership in one team, with a manager flag (CLAUDE.md §4.2:
"`TeamMember` (user↔team, with the team's manager flagged)").

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `team_id` | `int` (FK → `teams.id`, `RESTRICT`) | No | Part of composite PK |
| `user_id` | `uuid` (FK → `AspNetUsers.Id`, `RESTRICT`) | No | Part of composite PK |
| `is_team_manager` | `boolean` | No, default `false` | Drives `AUTH-RULE-02` "Manager, own teams" scoping — a user is that team's manager iff this flag is set on their membership row |
| `joined_at` | `timestamptz` | No | |

**Primary key:** `(team_id, user_id)` — a user belongs to a team at most once.
**Relationships:** `many:many` between `teams` and `AspNetUsers`, realized as this join table.
**Access pattern it supports:** `TICKET-INV-03` ("assignee must be an active member of the ticket's
team") and `AUTH-RULE-05` (team-scoped visibility) both resolve against this table joined to
`AspNetUsers.is_active`.

## 4. `categories`

**Grain:** one row = one category, belonging to exactly one team (CLAUDE.md §4.2: "`Category`
(belongs to a team, carries a default work type)"; `TICKET-INV-02`).

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `int identity` | No | PK |
| `team_id` | `int` (FK → `teams.id`, `RESTRICT`) | No | `TICKET-INV-02`: a ticket's category must belong to the ticket's team, enforced by joining through this column |
| `name` | `text` | No | |
| `default_work_type` | `text` (CHECK: `WorkType` values) | No | `TICKET-ENUM-01` |
| `created_at` | `timestamptz` | No | |
| `is_active` | `boolean` | No, default `true` | Phase 22 (ADR-0022): deactivation only, never a hard delete; independent of its team's own `is_active` — see ADR-0022 for why deactivating a team never cascades to its categories |

**Constraints:** `UNIQUE (team_id, name) WHERE is_active` (`PERSIST-RULE-05`; filtered in Phase 22
so a deactivated category's name is reusable on the same team).
**Relationships:** `1:many` → `tickets`.

## 5. `projects`

**Grain:** one row = one project. CLAUDE.md defines `Project` only as an optional ticket
association (`Ticket.ProjectId?`) with no further fields specified in §4.2; no additional structure
is invented here beyond what the contract requires to support that association.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `int identity` | No | PK |
| `organization_id` | `int` (FK → `organizations.id`, `RESTRICT`) | No | Phase 16, `ORG-RULE-01`: added — `Project` had no team relation to inherit scope from and was entirely global before this |
| `name` | `text` | No | |
| `created_at` | `timestamptz` | No | |
| `is_active` | `boolean` | No, default `true` | Project management phase: deactivation only, never a hard delete — a ticket referencing this project keeps displaying its name regardless of this flag |

**Constraints:** `UNIQUE (organization_id, name) WHERE is_active` (changed from global `UNIQUE (name)`
in Phase 16; filtered to active rows in the project management phase so a deactivated project's name
becomes reusable without touching that row).
**Relationships:** `1:many` → `tickets` (optional — `Ticket.ProjectId` is nullable); `many:1` →
`organizations`.


## 5b. `sprint_ticket_snapshots` (`SPRINT-INV-08`, Phase 26B, ADR-0030)

**Grain:** one row = one ticket's frozen result in one *completed* sprint. Append-only: written in the
same save as the sprint's completion, never updated or deleted. `tickets.sprint_id` is only the
*current* planning membership and changes on carry-forward; this table is the historical record.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `sprint_id` | `int` (FK → `sprints.id`, `RESTRICT`) | No | PK part |
| `ticket_id` | `int` (FK → `tickets.id`, `RESTRICT`) | No | PK part; `ix_sprint_ticket_snapshots_ticket` serves "which sprints did this ticket belong to" |
| `status_at_completion` | `text` (CHECK: `Status` values) | No | |
| `was_done` | `boolean` | No | Resolved or Closed at completion |

`sprints` also gains `cancelled_at timestamptz NULL` and status `Cancelled` (`CHECK (status <> 'Cancelled' OR cancelled_at IS NOT NULL)`).
## 6. `sla_configurations`

**Grain:** one row = one SLA target for a `(WorkType, Priority)` pair, or the `(null, Priority)`
default row (`SLA-RULE-01`).

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `int identity` | No | PK |
| `work_type` | `text` (CHECK: `WorkType` values) | Yes | `NULL` = default row for that priority (`SLA-RULE-01`) |
| `priority` | `text` (CHECK: `Priority` values) | No | |
| `target_minutes` | `int` | No | Seeded: Critical 240 / High 480 / Medium 1440 / Low 4320 (`SLA-RULE-02`) |
| `risk_threshold_percent` | `int` | No | Seeded default 80 (`SLA-RULE-02`) |

**Correction (Phase 3A reconciliation):** this table previously listed `created_at`/`updated_at`
columns here. CLAUDE.md §8.1 defines `SlaConfiguration` as exactly
`{ Id, WorkType?, Priority, TargetMinutes, RiskThresholdPercent }` — five fields, no timestamps —
and no rule in `docs/domain-model.md` (`SLA-RULE-01`/`02`) requires an audit trail on this
reference-data row. Unlike `Ticket`, whose `CreatedAt`/`UpdatedAt` are load-bearing for
`TICKET-INV-10` and the SLA clock itself, an `SlaConfiguration` row has no comparable domain
reason to track when it was last touched. The Domain model (which never had these fields) was
correct; this document was wrong and is now corrected to match it, rather than adding two fields
to `SlaConfiguration` merely because timestamp columns are a common convention.

**Constraints:** unique on `(work_type, priority)` with `work_type` nullable — implemented as a
unique index using `COALESCE(work_type, '')` (or a partial unique index for the `NULL` case), per
CLAUDE.md §7.4 (`PERSIST-RULE-05`).
**Relationships:** none by FK — `Ticket` does **not** FK to `sla_configurations`. `SLA-RULE-03`
requires that editing a configuration never retroactively changes an existing ticket, so the ticket
captures a *copy* of the resolved value (`sla_target_minutes`) at clock-start time rather than
referencing the configuration row. This is a deliberate absence of a relationship, not an omission.

## 7. `tickets`

**Grain:** one row = one ticket (`TICKET-ENT-01`, the aggregate root).

| Column | Type | Nullable | Notes |
|---|---|---|---|

| `title` | `text` | No | 5–200 chars (`TICKET-INV-01`) — length enforced in the domain; not duplicated as a DB `CHECK` (CLAUDE.md does not list a length `CHECK` in §7.4, so none is added here) |
| `description` | `text` | No | ≤ 8000 chars (`TICKET-INV-01`) |

| `requester_id` | `uuid` (FK → `AspNetUsers.Id`, `RESTRICT`) | No | `TICKET-ENT-04` |
| `assignee_id` | `uuid` (FK → `AspNetUsers.Id`, `RESTRICT`) | Yes | `TICKET-INV-03`, `TICKET-INV-04` |
| `team_id` | `int` (FK → `teams.id`, `RESTRICT`) | No | `TICKET-INV-02` |
| `project_id` | `int` (FK → `projects.id`, `RESTRICT`) | Yes | Optional per `Ticket.ProjectId?` |

| `updated_at` | `timestamptz` | No | `TICKET-INV-10` |

| `due_date` | `timestamptz` | Yes | Feeds the `Overdue` attention signal; also a planning fact, distinct from `sla_due_at` (`TICKET-INV-11`) |
| `sprint_id` | `int` (FK → `sprints.id`, `RESTRICT`) | Yes | Phase 26 (ADR-0029): planning membership only — never read by workflow/SLA/attention. `NULL` for every pre-existing ticket. Partial index `ix_tickets_sprint WHERE sprint_id IS NOT NULL` serves the board and sprint counts |
| `sprint_backlog` | `boolean` | No, default `false` | "Selected for the sprint, not yet pulled onto the board" (`TICKET-INV-13`). `CHECK (sprint_backlog = false OR sprint_id IS NOT NULL)` |
| `sla_target_minutes` | `int` | No | Captured at clock-start; not a live FK to `sla_configurations` (`SLA-RULE-03`) |
| `sla_started_at` | `timestamptz` | No | `SLA-RULE-05` |
| `sla_due_at` | `timestamptz` | No | `SLA-RULE-05`, indexed — see §9 |
| `sla_paused_minutes` | `int` | No, default `0` | `SLA-RULE-07` |
| `pending_since` | `timestamptz` | Yes | Set while `Status = Pending` (`SLA-RULE-07`) |
| `sla_met` | `boolean` | Yes | Set once at resolution, never recomputed (`SLA-RULE-08`) |
| `resolved_at` | `timestamptz` | Yes | `TICKET-INV-06` |
| `closed_at` | `timestamptz` | Yes | `TICKET-INV-07` |
| `resolution_code` | `text` (CHECK: `Resolution` values) | Yes | `TICKET-INV-06`, `TICKET-ENUM-04` |
| `resolution_notes` | `text` | Yes | ≥ 10 chars when set (`TICKET-INV-06`) |
| `reopen_count` | `int` | No, default `0` | `TICKET-WF-09` |
| `assignment_change_count` | `int` | No, default `0` | `TICKET-WF-11` |
| `pending_reason` | `text` | Yes | Required (non-empty) when `Status = Pending` (`TICKET-INV-05`) |
| `status_before_pending` | `text` (CHECK: `Status` values) | Yes | Implementation-discovered requirement (not in the original CLAUDE.md §4.2 field list): `Resume` must know whether the ticket was `Assigned` or `InProgress` before it went on hold, to land on the correct one (TICKET-WF-05 / TICKET-WF-06). Set alongside `pending_since` in `PutOnHold`; cleared alongside it in `Resume`/`Resolve`. Only ever holds `Assigned` or `InProgress` — not a general workflow-history mechanism, just the one bit `Resume` needs. |
| *(concurrency token)* | PostgreSQL `xmin` | — | Mapped as a concurrency token, not a regular column (`PERSIST-RULE-06`) — see §10 |

**Constraints:**
- `UNIQUE (reference)`.
- `CHECK (status <> 'Closed' OR closed_at IS NOT NULL)` and the resolved/resolution equivalent
  (`PERSIST-RULE-03`).
- `CHECK (sla_due_at > sla_started_at)` (`PERSIST-RULE-04`).
- `CHECK` on `work_type`, `priority`, `status`, `resolution_code` against their enum value lists
  (`PERSIST-RULE-02`).

**Relationships:**
- `many:1` → `teams`, `categories` (required); `projects`, `AspNetUsers` (assignee) (optional).
- `1:1` → `AspNetUsers` (requester, required).
- `1:many` → `ticket_comments`, `ticket_events` (both children of this aggregate, `CASCADE` delete).

## 9. `ticket_events`

**Grain:** one row = one audit event for one ticket (`AUDIT-RULE-01`, `AUDIT-RULE-02`).

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `int identity` | No | PK |
| `ticket_id` | `int` (FK → `tickets.id`, `CASCADE`) | No | Child of the `Ticket` aggregate (`AUDIT-RULE-04`) |
| `event_type` | `text` (CHECK: the 17 event types) | No | `AUDIT-RULE-03` |
| `actor_user_id` | `uuid` (FK → `AspNetUsers.Id`, `RESTRICT`) | No | |
| `occurred_at` | `timestamptz` | No | |
| `field` | `text` | Yes | Populated for field-change events only |
| `old_value` | `text` | Yes | |
| `new_value` | `text` | Yes | |
| `note` | `text` | Yes | |

**Relationships:** `many:1` → `tickets` (cascade), `AspNetUsers` (actor, restrict).
**Append-only enforcement:** at the application layer — no `UpdateAsync`/`DeleteAsync` method exists
on any service touching this table, and `TicketEvent` exposes no public setters (`AUDIT-RULE-01`).
No database-level `REVOKE UPDATE/DELETE` or trigger is proposed here, because `docs/domain-model.md`
does not establish one as a persistence rule (`PERSIST-RULE-01`…`06` lists no such constraint) —
flagged per the domain-contract-protection instruction rather than added silently. If DB-enforced
immutability is wanted, it needs its own ADR before Phase 3, since it would be a new architectural
decision, not a restatement of an existing one.

## 9a. `platform_audit_events` (Phase 24, ADR-0023)

**Grain:** one row = one platform-administration action (organization/user deactivate/reactivate) —
deliberately separate from `ticket_events`, which is scoped to one ticket by a required FK and has
no way to represent an organization- or user-level action with no ticket involved.

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `id` | `int identity` | No | PK |
| `event_type` | `text` (CHECK: `OrganizationDeactivated`/`OrganizationReactivated`/`UserDeactivated`/`UserReactivated`/`UserApproved`/`UserRejected`) | No | The closed set of platform mutations Phase 24/24A introduce |
| `actor_user_id` | `uuid` (FK → `AspNetUsers.Id`, `RESTRICT`) | No | The Platform Admin who performed the action |
| `target_organization_id` | `int` (FK → `organizations.id`, `RESTRICT`) | Yes | Set only for organization events |
| `target_user_id` | `uuid` (FK → `AspNetUsers.Id`, `RESTRICT`) | Yes | Set only for user events |
| `occurred_at` | `timestamptz` | No | |

**Constraints:** `CHECK ((target_organization_id IS NOT NULL)::int + (target_user_id IS NOT NULL)::int = 1)`
— exactly one target per event, never both, never neither.
**Relationships:** `many:1` → `AspNetUsers` (actor, restrict), `organizations` (target, restrict),
`AspNetUsers` (target, restrict).
**Append-only, same enforcement style as `ticket_events`:** written only alongside the lifecycle
mutation itself (one `SaveChangesAsync`, so the action and its audit record are atomic), never
updated or deleted by any service.

## 10. Concurrency strategy

Optimistic concurrency via PostgreSQL's built-in `xmin` system column, mapped as EF Core's
concurrency token on `Ticket` only (`PERSIST-RULE-06`, formalized in ADR-0011). No other table gets
a concurrency token — the domain contract does not require one for reference/configuration data,
and adding one would be an uncalled-for abstraction (CLAUDE.md §21.6).

Mechanics: every `UPDATE` to a `tickets` row implicitly includes `WHERE xmin = @original_xmin` (EF
Core generates this once the property is configured `IsRowVersion()`). If another transaction
committed first, zero rows match, EF Core raises `DbUpdateConcurrencyException`, and the
Application layer maps it to an HTTP 409 / a "this ticket changed while you were editing, please
reload" page message (CLAUDE.md §11.3). This directly protects the single-aggregate,
single-`SaveChangesAsync` write pattern in CLAUDE.md §7.2 — since every mutation loads, mutates, and
saves the whole `Ticket` graph in one transaction, one concurrency token on the root is sufficient;
child rows (`ticket_comments`, `ticket_events`) never need their own, because they are never updated
after insert (comments are immutable once posted in this domain's rule set, and events are
append-only).

## 11. Audit persistence strategy

`ticket_events` is populated exclusively as a side effect of a `Ticket` domain method call, in the
same `SaveChangesAsync` as the state change it records (`AUDIT-RULE-04`). There is no outbox table,
no domain-event dispatcher, and no background worker — the aggregate boundary *is* the transaction
boundary, formalized in ADR-0012. Distinguishing the three related-but-different concepts this
schema must not conflate:

| Concept | What it is | Where it lives |
|---|---|---|
| Domain event/change | An in-memory fact produced by calling a `Ticket` method (e.g. "status moved to Resolved") | Exists only inside the `Ticket` object graph during the method call — never a standalone message or queue entry |
| Audit record | The persisted, append-only trace of that fact | `ticket_events` row |
| Current ticket state | The ticket's present, mutable field values | `tickets` row's own columns (e.g. `status`, `assignee_id`) |

`ticket_comments` is not audit — it is human operational content, queried and rendered separately,
even though the UI merges both into one timeline (`AUDIT-RULE-06`).

## 12. Indexes

All from CLAUDE.md §7.5, unmodified — each is a partial index keeping the hot "open work" set small,
plus the two non-partial indexes needed for resolution reporting and audit/comment lookups. No
additional index is proposed; none of the query shapes implied by `docs/domain-model.md` or
`docs/architecture.md` require one beyond this set.

| Index | Access pattern it supports |
|---|---|
| `ix_tickets_open_sla_due (sla_due_at) WHERE status NOT IN ('Resolved','Closed')` | `AttentionQueryService`'s prefilter and any "sort by SLA remaining" queue view — only non-terminal tickets ever need an SLA-due sort (`ATTN-RULE-05`, `SLA-RULE-10`) |
| `ix_tickets_open_team_priority (team_id, priority) WHERE status NOT IN ('Resolved','Closed')` | Team-scoped work queues filtered/sorted by priority (`AUTH-RULE-05`) |
| `ix_tickets_open_assignee (assignee_id) WHERE status NOT IN ('Resolved','Closed')` | "My queue" (personal assigned-work view) and workload aggregation (`ATTN-RULE-07`) |
| `ix_tickets_open_unassigned (created_at) WHERE assignee_id IS NULL AND status NOT IN ('Resolved','Closed')` | `UnassignedUrgent` signal prefilter — oldest-first unassigned queue |
| `ix_tickets_resolved_at (resolved_at)` | Resolution-trend and SLA-compliance reporting over a date range (not status-filtered, so not a candidate for a partial index) |
| `ix_ticket_events_ticket (ticket_id, occurred_at DESC)` | Rendering one ticket's audit timeline newest-first |
| `ix_ticket_comments_ticket (ticket_id, created_at DESC)` | Rendering one ticket's comment thread newest-first |
| `gin_tickets_title_trgm ON tickets USING gin (title gin_trgm_ops)` | `ILIKE` search on title (CLAUDE.md §7.2) |

Supporting (not in §7.5 but required by the constraints above, so not "speculative" — each backs a
`UNIQUE` this document already requires): the unique indexes implicit in `UNIQUE (reference)`,
`UNIQUE (team_id, name)` on categories, and the `(work_type, priority)` partial/coalesced unique
index on `sla_configurations`.

**Work-queue ordering (Phase 5):** the paginated work queue orders by `created_at DESC, id DESC`
(page size 25) — deterministic per CLAUDE.md §7.2, and deliberately not an urgency ordering, which
belongs to `AttentionPolicy` in Phase 8. **No index was added for it.** Measured on 3,000 tickets
across three teams (the CLAUDE.md §16 target scale), the team-scoped page query plans as a
sequential scan feeding a top-N heapsort at **2.0 ms** (86 shared buffers hit), and the matching
count query at **0.9 ms**. The planner declines `ix_tickets_open_team_priority` because the team
predicate selects roughly a third of the table — too little selectivity for an index to pay for
itself. Per §7.5's "justify additions", the evidence says not to add one; revisit only if a real
workload shows otherwise.

**At-risk queue (Phase 8):** `AttentionQueryService` runs the ATTN-RULE-05 prefilter — a single
query that applies the caller's team scope, excludes terminal tickets, ORs the eight signal
predicates, and `Include`s each candidate's events for the `Stalled` signal. **The predicate is
deliberately a superset**, not an equivalent: the at-risk branch widens to the smallest persisted
`risk_threshold_percent` and the aging branch to the shortest configured aging window, because both
real thresholds vary per row and per priority. Over-inclusion is harmless — `AttentionPolicy`
discards anything that does not truly qualify — whereas under-inclusion would silently lose at-risk
work, which is why ATTN-RULE-06's superset test exists.

**Ranking precedes pagination**, unlike every other list in FlowOps. ATTN-RULE-04 ranks by severity
across the *whole* candidate set, so page 1 must be the most urgent tickets overall rather than the
most urgent of an arbitrary database page. Candidates are therefore materialised, evaluated, ranked,
and only then paged in memory. Measured on 3,000 tickets across three teams: 1,000 in the caller's
scope narrowed to **207 candidates in 1.34 ms**, the planner using the existing
`ix_tickets_open_team_priority` partial index for the scope and non-terminal predicate and applying
the OR-chain as a filter, with events joined in the same statement. **No index was added** — nothing
in that measurement justifies one.

**Attention signals on the main work queue remain deferred past Phase 11.** CLAUDE.md §22 asks for
them on ticket rows generally; Phase 8 shows them only on the dedicated at-risk queue, because
rendering them on every work-queue page would mean evaluating the policy (and loading events) for
all 25 rows of a list the contract also requires to stay ordered by `created_at DESC`. Phase 11
reordered and restyled the *dashboard* and *at-risk* pages but explicitly did not touch this — the
Work Queue still carries no per-row `AttentionPolicy` evaluation. This is a deliberate deferral,
recorded here so §22 is not quietly left unmet.

**Ticket-creation Team/Category read path (Phase 11, C-3):** the raw numeric Team/Category ids on
the ticket-creation form were a usability defect — a caller had to already know a database id.
`TicketQueryService.GetCreationOptionsAsync` now resolves the caller's eligible teams (all teams
for Admin, else the caller's own `MemberTeamIds`) together with each team's categories in two
queries, bounded by the small size of this reference data. This is a read-only convenience, not a
new authorization boundary: `TicketAccessPolicy.CanCreate` and TICKET-INV-02 (a category belongs to
exactly one team) remain the sole authoritative checks inside `TicketService.CreateAsync`, run
again on every submission regardless of what this list offered. The Create page asks for a single
category (grouped by team via HTML `<optgroup>`, no JavaScript) and derives `TeamId` from the
chosen category server-side — there is no independent Team field to submit.

**Dashboard KPIs (Phase 10):** CLAUDE.md §22 caps the dashboard at exactly four KPIs — Open Work,
Overdue, SLA Compliance, Average Resolution Time — but specifies no reporting window for the two
historical ones. This project fills that gap with a **fixed 90-day window** (a Phase 10 decision,
not a documented rule), chosen because it is exactly the access pattern `ix_tickets_resolved_at`
was already built for ("resolution-trend and SLA-compliance reporting over a date range" — see
above). SLA Compliance counts the persisted `sla_met` fact directly (never re-derives it); Average
Resolution Time is `resolved_at − sla_started_at`, not `− created_at`, so a reopened ticket's
average reflects only its current cycle — consistent with `sla_started_at` itself resetting on
`Reopen` (SLA-RULE-09) and with `resolved_at`/`sla_met` being nulled together on the same call, so
neither KPI can see a reopened-and-not-yet-resolved-again ticket's prior outcome.

`AnalyticsQueryService` runs five queries sequentially against the one scoped `FlowOpsDbContext` —
Open Work, Overdue, the SLA-compliance `GROUP BY sla_met`, the average-resolution `AVG`, and the
workload `GROUP BY (team_id, assignee_id)` — comfortably under CLAUDE.md §16's ≤6-query ceiling.
A literal reading of §16's "executed concurrently where independent and safe" would need
`IDbContextFactory`, a persistence pattern this project uses nowhere else; introducing it for a
first dashboard was judged disproportionate to the benefit at this scale, so all five run
sequentially (Phase 10 decision).

Measured on 3,000 tickets, one team in scope (~1,929 open): Open Work **1.49 ms**, Overdue
**1.47 ms** (both a sequential scan — the team predicate alone selects roughly two-thirds of the
table, too little selectivity for an index to pay for itself), SLA compliance **0.61 ms** and
average resolution **0.63 ms** (both using `ix_tickets_resolved_at`, exactly the index's documented
purpose), workload grouping **1.34 ms**. **No index was added** — nothing in this measurement
justifies one.

Every KPI card links through to the work it represents via `TicketQueueFilter` — a closed,
three-value enum (`OpenWork`, `Overdue`, `ResolvedRecently`) on the existing paginated work queue,
deliberately not a general filter/search framework.

The optional ATTN-RULE-07 weighted workload score and Chart.js/client-side chart rendering are both
deferred — the former stays exactly as optional as CLAUDE.md §9.4 already states, the latter
indefinitely: Phase 11 added a shared Razor layout and one local stylesheet (no JS, no CDN assets,
no chart library — see below), but a client-side chart was never part of that scope. Phase 10 shipped
the four KPIs and the workload distribution as plain, accessible HTML; Phase 11 restyled them without
introducing a chart.

**Shared layout and dashboard reordering (Phase 11, C-9):** every page prior to Phase 11 was a
standalone HTML document (Phases 5, 6, 8, 9 all deferred this). Phase 11 introduced
`Pages/_Layout.cshtml` (a semantic `<nav>` landmark, a skip link, and the sign-out form, rendered
only for an authenticated request) and one local stylesheet, `wwwroot/flowops.css` — no Bootstrap,
Tailwind, JS framework, or CDN asset, per CLAUDE.md §11.1. The dashboard (`Pages/Index.cshtml`) now
opens on a top-5 at-risk preview from the existing `AttentionQueryService.GetAtRiskAsync` (the same
call and ranking the At-Risk page itself uses) with a link to the full queue, and places the four
KPIs and the workload table after it — no new query, no new ranking logic, and no change to
`AnalyticsQueryService`.

**Phase 12 test-reliability fix:** `TicketCommentServiceTests.AddCommentAsync_AllowedRole_PersistsCommentAndExactlyOneEvent`
verified its two `TicketEvent` rows' order with `OrderBy(e => e.OccurredAt)` alone. Both rows
(`Created` and `CommentAdded`) share one fixed test timestamp, so the two are a genuine tie —
PostgreSQL gives no ordering guarantee for a tied sort key without a secondary one, and which row
came back first depended on the query plan, which in turn depended on machine load (it reproduced
only when the three test projects ran concurrently via `dotnet test FlowOps.sln`, never when
`FlowOps.Application.Tests` ran alone). The fix is test-only: `.ThenBy(e => e.Id)`, the same
insertion-order tiebreaker `TicketQueryService.GetHistoryAsync`'s production ordering already uses
(`OrderByDescending(e => e.OccurredAt).ThenBy(e => e.Kind).ThenByDescending(e => e.Id)`) — that
query was never affected by this defect and was not changed.

**Phase 12 security hardening:** `Program.cs` now sets `Content-Security-Policy`,
`X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, and `Permissions-Policy` on every
response (via `Response.OnStarting`, so the headers survive `UseExceptionHandler`'s
`Response.Clear()` on an unhandled exception) and registers `UseExceptionHandler("/Error")` as the
one global exception handler CLAUDE.md §11.3 asks for — domain-rule violations, authorization
denials, and concurrency conflicts are all already caught explicitly inside the PageModels that can
produce them and never reach it. `TicketService` now logs the §13-required Information (ticket
created/assigned/status changed/resolved/reopened) and Warning (authorization denial, concurrency
conflict) events; the login rate limiter logs a Warning on rejection. **HTTPS enforcement, HSTS,
and `UseForwardedHeaders` remain deliberately deferred** — Phase 13 (Docker) and Phase 15
(Render + Neon) are what actually introduce a TLS-terminated, proxied environment to configure and
validate these against; adding them now against `dotnet run`'s plain-HTTP local environment would
mean shipping untested middleware — the same reasoning already documented in `Program.cs` for
`CookieSecurePolicy.SameAsRequest` (Phase 4), which is deferred for exactly the same reason.

**EF Core convention indexes (Phase 3A discovery):** the generated migration also contains
`ix_tickets_category_id` and `ix_tickets_project_id`, which nothing above asked for. EF Core adds
one index per foreign-key column automatically unless that column already leads another index —
`team_id` gets no such index because `ix_tickets_open_team_priority` already leads with it, but
`category_id` and `project_id` lead no other index, so EF Core supplies its own. These are
ordinary FK-support indexes (referential-integrity lookup performance), not deliberately selected
business-query indexes like the ones above — they are retained as a normal, low-cost EF Core
convention, not as an additional entry in this document's access-pattern table, and no further
index has been added beyond them.

## 13. Derived, not stored

These values are computed by `SlaPolicy` / `AttentionPolicy` at read time and **never** get a
column, table, or cached value, per `SLA-RULE-10`/`SLA-RULE-12`/`ATTN-RULE-01`:

- SLA status (`Within` / `AtRisk` / `Breached` / `Paused` / `Met`) — computed from `sla_due_at`,
  `sla_started_at`, `sla_paused_minutes`, `status`, and the persisted `sla_met`.
- The full list of attention signals for a ticket, and their ranking order.
- Workload score (`ATTN-RULE-07`, optional/Phase 10).
- Elapsed-time strings shown in the UI ("42m left", "2h 14m over") — formatting, not persistence.

The one SLA fact that **is** persisted rather than derived is `sla_met` (`SLA-RULE-08`) — it is a
point-in-time outcome fixed at resolution, not a live status, so storing it is correct and required
(recomputing it later would silently rewrite compliance history).

## 14. EF Core mapping strategy summary

(Full detail belongs to the entity configuration classes built in Phase 3; this is the design intent
per the `flowops-ef-core` skill.)

- One `IEntityTypeConfiguration<T>` per entity (`Ticket`, `TicketComment`, `TicketEvent`, `Team`,
  `TeamMember`, `Category`, `Project`, `SlaConfiguration`), nothing in `OnModelCreating` bodies.
- `Ticket` is mapped as a single aggregate with `TicketComment`/`TicketEvent` as owned collections
  configured `HasMany().WithOne()` with `CASCADE` delete — not EF "owned entity types" in the
  strict sense (they need their own identity/PK for the audit/comment query patterns in §12), just
  aggregate-scoped children.
- All four enums (`WorkType`, `Priority`, `Status`, `Resolution`) are mapped `HasConversion<string>()`
  and backed by a `CHECK` constraint added via raw SQL in the migration (`PERSIST-RULE-02`) — never
  mapped as `int`.
- `Ticket.RowVersion` maps PostgreSQL `xmin` via `.UseXminAsConcurrencyToken()` (Npgsql EF provider),
  not an application-managed version column.
- No value objects are introduced — the domain contract does not require any (see
  `docs/architecture.md` §2, "Explicitly not created").
- Read queries project with `Select` directly to DTOs (`AsNoTracking`); write queries load the
  tracked `Ticket` graph (including its comments/events only when the operation needs to append one)
  and call domain methods, per CLAUDE.md §7.2.
