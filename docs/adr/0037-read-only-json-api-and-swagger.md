# 0037. A small read-only JSON API, documented with Swagger UI

## Status
Accepted

## Context
FlowOps was server-rendered only: Razor Pages plus one small JSON status endpoint. CLAUDE.md §11.2
described a larger `/api/v1` that was never built, so the documentation promised something the code did not
do. A real, tested API surface was wanted for two reasons: to make the CI gate meaningful (black-box HTTP
checks against the built container) and to give reviewers a live, documented contract to inspect. The API had
to stay inside the existing authorization and tenancy model rather than create a second one.

## Decision
Add four read-only endpoints under `/api/v1` — `GET /tickets`, `GET /tickets/{id}`, `GET /attention`,
`GET /workload` — as a minimal-API group in `FlowOps.Web/Api`. Each handler resolves the current user the
same way a PageModel does and calls the existing Application service (`TicketQueryService`,
`AttentionQueryService`, `AnalyticsQueryService`), returning its DTOs. No rule is decided in the API layer,
so it cannot be more permissive than the pages.

Authentication is the existing login cookie (ADR-0008); there is no token or API key. An unauthenticated
`/api` call returns `401` and an authorization failure `403`, via cookie events scoped to `/api` only — every
page keeps its normal redirect. A ticket that does not exist and one the caller may not see are both `404`,
so identifiers cannot be probed across organizations. Enums are serialized as names. A query value that
cannot be bound is a `400` in every environment (`RouteHandlerOptions.ThrowOnBadRequest = false`).

The OpenAPI document is generated by the first-party `Microsoft.AspNetCore.OpenApi` (`/openapi/v1.json`,
limited to `/api/` routes) and rendered by `Swashbuckle.AspNetCore.SwaggerUI` at `/swagger`, which only
renders a document and does not generate one. Both are anonymous documentation, a deliberate departure from
§11.2's "requires authentication": they expose endpoint shapes and no data, and every endpoint they describe
still requires the cookie. Swagger UI needs inline script and style, so the Content-Security-Policy is
relaxed for the `/swagger` path only; every other response, including the API, keeps the strict policy.

Write endpoints, `analytics/summary`, per-team workload by id, `ProblemDetails` error bodies and an API key
for outside tools are **not** adopted.

## Alternatives considered
- **No API; keep the site server-rendered only:** rejected — it left nothing meaningful for black-box CI
  checks beyond health and page redirects, and the documentation kept describing an API that did not exist.
- **Full API including writes (§11.2 as written):** rejected — write endpoints need conflict handling,
  validation bodies and far more tests, with no consumer yet. Read-only gives the contract and the CI value.
- **API key or JWT for outside tools such as Power BI:** rejected for now — it reverses ADR-0008's no-token
  decision, adds a secret to manage and a larger attack surface. Revisit only with a real external consumer.
- **Swashbuckle for the document as well as the UI:** rejected — the framework now generates OpenAPI itself;
  only the UI needed a package.
- **Require login to view the Swagger page:** rejected — the UI is served by middleware, not an endpoint, so
  protecting it would need extra plumbing for no data protection benefit.

## Consequences
The CI gate and the in-process tests can assert real API behavior, including that one organization can never
read another's tickets through it. The API is a thin layer, so it inherits every future change to
authorization or tenancy for free. The cost is one more public surface on the demo (read-only, authorized,
cookie-bound, `SameSite=Strict`, no CORS policy so no cross-origin callers), two NuGet packages that must keep
passing the dependency audit, and a documented CSP exception on one path. Cookie authentication means outside
tools cannot call it today; that is a known, accepted limit.
