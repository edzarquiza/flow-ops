# 0017. Invitation token security, expiration, and acceptance concurrency

## Status
Accepted

## Context
Phase 18 needed a way for an Admin/Manager to grant organization access to an email address that
may or may not already have a FlowOps account, without building real email delivery (explicitly
out of scope) or mandatory email verification (also out of scope). The invitation link itself is
therefore the only credential a recipient ever presents, and it is emailed by the *inviter*, by
hand, outside the application — making it a genuine bearer credential that must be handled with
the same care as a password reset token, not as an opaque database id.

Three sub-decisions follow from that: how the token is generated and stored, how long it remains
valid, and — since nothing stops the same link being opened twice at once — how acceptance stays
safe under concurrent use.

## Decision

**Token generation and storage.** `RandomNumberGenerator.GetBytes(32)` (256 bits from the
platform's CSPRNG — never `Guid.NewGuid()`, which is not a security primitive, and never anything
derived from the email or a timestamp, which would be guessable) is Base64Url-encoded into the raw
token embedded in the invitation link. Only `SHA-256(rawToken)`, hex-encoded, is ever persisted, in
`invitations.token_hash` (unique-indexed, for O(1) acceptance lookup). `InvitationService` holds
the raw token in a local variable only long enough to hash it and return it once to its caller; no
property, log statement, or exception message ever carries it. See Step 22's token-leakage
analysis in the Phase 18 report for where this was specifically checked, including a
Development-only logging fix (`appsettings.Development.json`) that would otherwise have put the
raw token — as a request query string — into local hosting-diagnostics log lines.

**Expiration.** A fixed 7-day lifetime (`Invitation.DefaultLifetime`), chosen as a plain constant
rather than a new configuration convention: no existing FlowOps setting governs a duration like
this, and a single, documented default is simpler than introducing configurability nothing yet
needs. Checked server-side, unconditionally, on every acceptance attempt (`Invitation.Accept`) —
an expired invitation is rejected even with a perfectly valid, correctly-hashed token. Expired rows
are left in place; no cleanup job was built (explicitly out of scope), and an expired invitation
simply stops being acceptable, forever, without needing to be deleted.

**Single-use / concurrent acceptance.** `Invitation` is mapped with the same PostgreSQL `xmin`
optimistic-concurrency token `TicketConfiguration` already uses for tickets (ADR-0011) — not a new
mechanism. `Invitation.Accept` and the new `OrganizationMembership` row are written together in one
`SaveChangesAsync`. Two concurrent acceptance attempts both load the same row and both believe
`AcceptedAt` is still null; only the first `SaveChangesAsync` to reach PostgreSQL commits, and the
second's stale `xmin` causes EF Core to throw `DbUpdateConcurrencyException` — caught by
`InvitationService` and surfaced as "already used," with no membership row created for the loser.
This reuses ADR-0011's existing pattern and its existing test precedent
(`TicketWorkflowServiceTests.ConcurrentTransitions_SurfaceAConcurrencyConflict`) rather than adding
a second concurrency mechanism, an application-level lock, or a distributed lock.

**Authorization / role-assignment policy.** `OrganizationAccessPolicy` (Domain, alongside
`TicketAccessPolicy`) is the single source of truth for who may invite, view members, change a
role, or remove a member — Admin unconditionally; Manager restricted, by explicit least-privilege
choice, to Agent/Viewer only (never Admin, never another Manager), since no existing product
requirement pinned an exact rule and granting Manager the ability to create or manage an Admin
would let a non-Admin role quietly accumulate Admin-equivalent influence over the organization.

## Alternatives considered
- **`Guid.NewGuid()` as the token**: rejected — a GUID is not generated by a CSPRNG and provides no
  documented security guarantee against prediction; Step 3 explicitly forbids this.
- **Hashing email + timestamp as the token**: rejected — deterministic and guessable by definition;
  explicitly forbidden by Step 3.
- **Storing the raw token** (to allow displaying it again later, e.g. "view sent invitations"):
  rejected — a stored bearer credential is a stored password, functionally; if the database were
  ever read (backup, replica, breach), every outstanding invitation would be immediately usable by
  whoever read it. Hash-only storage means a database compromise alone cannot forge acceptance.
- **A background job to expire/delete old invitations**: rejected — explicitly out of scope
  (Step 4); expiration is a read-time check, not a deletion, so no scheduler is needed for
  correctness.
- **An application-level advisory lock or a distributed lock for acceptance concurrency**: rejected
  — PostgreSQL's own `xmin` optimistic concurrency, already proven in this codebase for exactly
  this "exactly one of two racing writers wins" shape, is sufficient and requires no new
  infrastructure.
- **Letting Manager invite/manage any role, including Admin**: rejected — the safer default
  (least privilege) was chosen deliberately per Step 8's own instruction not to silently grant this
  without justification; recorded here so a future phase does not "fix" this as an oversight
  without re-reading why it was chosen.

## Consequences
- Accepting an invitation and creating its membership can never partially succeed: either both the
  `Invitation.AcceptedAt` flip and the `OrganizationMembership` insert commit together, or neither
  does.
- A Manager cannot promote anyone to Admin, demote/remove an Admin, or manage another Manager,
  through invitations or member management — only another Admin can. If this least-privilege
  default proves too restrictive in practice, revisit it explicitly (a new ADR amendment), not by
  quietly loosening `OrganizationAccessPolicy`.
- Because expired invitations are never deleted, the `invitations` table grows without bound over
  the application's lifetime. Acceptable at CLAUDE.md §16's target scale; revisit only if that
  changes.
